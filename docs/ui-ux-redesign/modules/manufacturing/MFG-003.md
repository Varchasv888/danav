# MFG-003 Production orders

Design specification. Baseline status from the discovery: **FULLY IMPLEMENTED** (Built: the design below restyles and extends a working feature.)

1. **Feature ID**: MFG-003
2. **Feature name**: Production orders
3. **Parent module**: MFG Manufacturing and Job Work
4. **Business purpose**: Plan, release and complete production. Materials leave stock and output comes in at cost. (screen text of `/manufacturing/orders/[id]`)
5. **Primary persona**: accountant, sales, purchase, storekeeper (roles holding its permissions, `07_ROLES_AND_PERMISSION_MATRIX`); owner and admin hold all.
6. **Entry point**: Manufacturing > planning > `/manufacturing/orders`
7. **Related screens**: `/manufacturing/orders/[id]` (Production orders), `/manufacturing/orders/new` (Production orders), `/manufacturing/orders` (Production orders)
8. **Subfeatures** (one per route, from the discovery):
   - `GET /production-orders` (apps/api/src/routes/manufacturing.ts:47)
   - `GET /production-orders/:id` (apps/api/src/routes/manufacturing.ts:48)
   - `POST /production-orders` (apps/api/src/routes/manufacturing.ts:49)
   - `POST /production-orders/:id/release` (apps/api/src/routes/manufacturing.ts:56)
   - `POST /production-orders/:id/issue` (apps/api/src/routes/manufacturing.ts:57)
   - `POST /production-orders/:id/complete` (apps/api/src/routes/manufacturing.ts:61)
   - `POST /production-orders/:id/cancel` (apps/api/src/routes/manufacturing.ts:65)
9. **Screen layout**: pattern **Document with lifecycle (list, editor, detail, timeline)** (`06_SHARED_COMPONENTS`). Desktop: page header (title, description, primary action) over a register with saved views, and an editor with the document header, line grid, totals and a sticky action footer; the saved document opens as an object page with a lifecycle line. [proposed layout]
10. **Component hierarchy** [proposed]: `PageHeader` > `FilterBar` > `DataTable` (or `Editor`/`ObjectHeader` + `Tabs`) > `StatusBadge`, `EmptyState`, `ErrorState`, `LoadingSkeleton`; dialogs through `ConfirmDialog`.
11. **Fields** (labels the current screens carry): Item, Quantity, Date, Notes, Good quantity, Rejected, Material, Cancel order.
12. **Columns** (current screens): Date, Good quantity, Material cost, Unit cost, Number, Item, Quantity, Produced, Status Default view shows the first 6 to 8; the rest sit behind the column chooser [proposed].
13. **Filters** [proposed from the data]: search, date range, status, scope (store, branch) where the permission is scoped.
14. **Primary actions**: `POST /production-orders`.
15. **Secondary actions**: `POST /production-orders/:id/release`, `POST /production-orders/:id/issue`, `POST /production-orders/:id/complete`, `POST /production-orders/:id/cancel`.
16. **Contextual actions** [proposed]: open the linked document, copy number, view audit history, and row actions limited to what the status and permissions allow.
17. **Validation and constraints**: the server remains the authority (`zod` schemas in the route file, domain rules in `packages/domain`); the form mirrors them inline and never relaxes them. Lifecycle `productionOrder` allows only: planned -> released, cancelled; released -> completed, cancelled; completed -> final; cancelled -> final.
18. **Approval behaviour**: No approval step in the routes.
19. **Permissions**: `inventory.cancel`, `inventory.create`, `inventory.edit`, `inventory.view`. Menu entries and buttons are hidden without permission; the API refuses regardless.
20. **Business status states**: planned > released > completed > cancelled; each shown as a status badge with icon and text (never colour alone).
21. **Loading states**: skeleton rows or blocks of the final shape; actions disabled while saving to stop duplicate submission.
22. **Empty states**: say what the screen is for and offer the primary action (or, for a report, widen the period).
23. **Error states**: show the server's reason in plain words and what to do; keep the user's input; permission failures say which permission is missing.
24. **Responsive behaviour** [proposed]: desktop 1280 and above full layout; tablet 768 collapses the object-page tabs into a scroll row and the grid to key columns; mobile 375 uses stacked records with a bottom action bar. Tables never shrink; they scroll or restack.
25. **Keyboard interactions**: Tab order follows reading order; Enter submits the focused form; Esc closes dialogs; list rows open with Enter. Do not rebind browser shortcuts.
26. **Offline behaviour**: not declared in `OFFLINE_ACTIONS`, so treat as online only. The web app has no offline mode; the device app uses only the declared actions.
27. **API dependencies**: `GET /production-orders`, `GET /production-orders/:id`, `POST /production-orders`, `POST /production-orders/:id/release`, `POST /production-orders/:id/issue`, `POST /production-orders/:id/complete`, `POST /production-orders/:id/cancel`. Contracts are not changed by the redesign.
28. **Existing backend limitations**: Routes, a screen and automated tests that call the routes are all present. Open items for this module are in `docs/product-discovery/10_IMPLEMENTATION_STATUS.md` section C.
29. **Related reports**: see the module's report column in the mega menu.
30. **Acceptance criteria**:
    - Every route listed under subfeatures still has an entry point.
    - Permissions match section 19 on screen and on the API; a user without them cannot reach the feature by menu, search or link.
    - Loading, empty, error and permission-denied states exist and were looked at.
    - No control is decorative: each one performs its action or is absent.
    - Keyboard-only use completes the primary task; focus is visible and returns sensibly after a dialog.
    - Layout verified at 1440, 1280, 768 and 375 px; tables scroll or restack.
    - Test evidence: `manufacturing.test.ts` still pass.
    - Light and dark themes both checked; status is never shown by colour alone.

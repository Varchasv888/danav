# 10 Implementation status

One status per feature, with evidence. The eight allowed statuses: FULLY IMPLEMENTED, PARTIALLY IMPLEMENTED, UI ONLY, BACKEND ONLY, DEMO / PLACEHOLDER, DOCUMENTED ONLY, NOT IMPLEMENTED, UNKNOWN. No feature carries two.

## Rules used (so the status can be reproduced)

Features (section A) come from the API routes. The status follows from three facts the extraction can establish:

1. **Screen**: a web screen's code (or the components it imports) calls one of the feature's routes.
2. **Test**: an automated API test in `apps/api/test` names one of the feature's routes.
3. **Adapter**: the feature's routes sit behind a simulator or demo adapter (GST portal, e-invoice, e-way bill, bank feed, message processing, file reading).

Rule: adapter -> DEMO / PLACEHOLDER. Else screen and test -> FULLY IMPLEMENTED (verified working code path: route, screen and test exist). Else test but no screen -> BACKEND ONLY. Else screen but no test -> PARTIALLY IMPLEMENTED (the path exists but is not verified by a test). Else (no screen, no test) -> BACKEND ONLY, noted as untested.

Limits [I]: a test that names a route proves the route is exercised, not that every rule is right; a screen that calls a route proves a path exists, not that it is complete. A feature used only by the device app is flagged `Device` in the evidence and is still counted BACKEND ONLY here because the web app has no screen for it.

Menu tiles with no screen (section B) are UI ONLY or NOT IMPLEMENTED. Plan items (section C) use: marked done and corroborated by a named screen or route -> FULLY IMPLEMENTED; marked done but not corroborated -> DOCUMENTED ONLY; marked in progress -> PARTIALLY IMPLEMENTED; marked not started -> NOT IMPLEMENTED when a search for specific terms found nothing (the terms are listed), or PARTIALLY IMPLEMENTED / UNKNOWN when related code exists.
